# Learn Go by Building a Task API

You'll build a REST API for managing tasks, starting from `hello world` and ending with a tested, containerized service backed by Postgres. Each story teaches one core Go concept. Do them in order; every story builds on the last.

**Rules of the game:** use only the standard library until Story 9, write the code yourself, and commit after every story.

---

## Phase 1: Language Foundations

### Story 1: Project setup

**As a developer, I want a runnable Go module so I have a place to build.**

- **Concept:** modules, packages, `go run`, `go build`, `go fmt`
- **Done when:**
  - `go mod init github.com/you/taskapp` is done
  - `cmd/api/main.go` prints "task app starting"
  - You can explain what `package main` and `func main` are
- **Stretch:** add `go vet` and `gofmt` checks to a Makefile.

### Story 2: Model a task

**As a user, I want a Task type so I can describe what I need to do.**

- **Concept:** structs, methods, custom types, `iota` enums, the `time` package
- **Done when:**
  - `internal/task` defines `Task{ID, Title, Description, Status, Priority, DueDate, CreatedAt}`
  - `Status` (`Todo`, `InProgress`, `Done`) and `Priority` (`Low`, `Medium`, `High`) are custom types using `iota`
  - `func (t Task) IsOverdue() bool` exists and handles a missing due date
- **Stretch:** add a `String()` method on `Status` (the `Stringer` interface).

### Story 3: Hold tasks in memory

**As a user, I want to add and list tasks so I can see my to-dos.**

- **Concept:** slices, maps, pointers vs values, multiple return values
- **Done when:**
  - A `MemoryStore` supports `Add`, `Get(id)`, `List`
  - `Get` returns `(Task, bool)` for a missing task
  - You can explain when you'd pass `*Task` vs `Task`

### Story 4: Handle errors the Go way

**As a developer, I want clear errors so callers know what went wrong.**

- **Concept:** the `error` interface, sentinel errors, wrapping with `%w`, `errors.Is` / `errors.As`
- **Done when:**
  - `Get` returns `ErrNotFound` instead of a bool
  - A `ValidationError` custom type carries the field name
  - `Add` rejects an empty title and a due date in the past
  - Callers check errors with `errors.Is` / `errors.As`

### Story 5: Swap storage behind an interface

**As a developer, I want storage to be replaceable so I can change databases later.**

- **Concept:** interfaces (implicit satisfaction), "accept interfaces, return structs"
- **Done when:**
  - A `Store` interface defines `Add`, `Get`, `List`, `Update`, `Delete`
  - `MemoryStore` satisfies it with no explicit declaration
  - A compile-time check exists: `var _ Store = (*MemoryStore)(nil)`

## Phase 2: The HTTP API

### Story 6: Serve JSON over HTTP

**As a client, I want to hit an endpoint and get tasks back.**

- **Concept:** `net/http`, handlers, `encoding/json`, struct tags
- **Done when:**
  - `GET /tasks` returns a JSON array with the correct `Content-Type`
  - JSON field names are lowercase via struct tags (`json:"title"`)
  - `Status` and `Priority` serialize as strings, not numbers (custom `MarshalJSON`)
  - `GET /healthz` returns 200
- **Stretch:** return `[]` instead of `null` for an empty list (and learn why it happens).

### Story 7: Full CRUD with routing

**As a client, I want to create, read, update, and delete tasks.**

- **Concept:** Go 1.22+ `ServeMux` patterns (`GET /tasks/{id}`), request decoding, status codes
- **Done when:**
  - `POST /tasks` → 201, `GET /tasks/{id}` → 200/404, `PUT` and `DELETE` work
  - `PATCH /tasks/{id}/complete` marks a task done
  - Bad JSON → 400, validation failure → 422
  - Handlers live on a `Server` struct that holds the `Store` (dependency injection)

### Story 8: Filter and sort tasks

**As a user, I want to see only what matters right now.**

- **Concept:** query parameters, `sort.Slice` / `slices.SortFunc`, closures, pointers for optional values
- **Done when:**
  - `GET /tasks?status=todo&priority=high` filters results
  - `?sort=due` orders by due date, with nil due dates last
  - Filter options are a `ListFilter` struct passed to `Store.List`
- **Stretch:** add `?overdue=true`.

### Story 9: Make the store thread-safe

**As an operator, I want concurrent requests not to corrupt data.**

- **Concept:** goroutines, `sync.Mutex` / `RWMutex`, the race detector
- **Done when:**
  - `MemoryStore` is guarded by an `RWMutex`
  - You write a test hammering it from 100 goroutines
  - `go test -race` passes (first, make it fail by removing the lock, to see what a race looks like)

## Phase 3: Real Infrastructure

### Story 10: Persist to Postgres

**As a user, I want my tasks saved so they survive restarts.**

- **Concept:** `database/sql`, drivers (`pgx`), connection pools, `Scan`, nullable columns (`sql.NullTime` or pointers), placeholders vs SQL injection
- **Done when:**
  - Postgres runs via `docker compose`
  - `PostgresStore` implements the same `Store` interface
  - Main swaps `MemoryStore` for it with no handler changes
  - Filters from Story 8 translate into safe parameterized SQL
- **Tip:** SQLite is a fine substitute if you want to skip Docker for now.

### Story 11: Configuration and migrations

**As an operator, I want config from the environment and a versioned schema.**

- **Concept:** `os.Getenv`, the `flag` package, `embed`, migration tools (`golang-migrate` or `goose`)
- **Done when:**
  - `DATABASE_URL` and `PORT` come from env vars with sane defaults
  - The `tasks` table is created by a numbered migration file
  - A second migration adds a `tags` column, to practice evolving a schema
  - The app fails fast with a clear message if config is missing

### Story 12: Respect context and timeouts

**As an operator, I want slow queries cancelled when a client disconnects.**

- **Concept:** `context.Context`, `r.Context()`, `QueryContext`, deadlines
- **Done when:**
  - Every `Store` method takes `ctx` as its first parameter
  - DB calls use `QueryContext` / `ExecContext`
  - A 3-second timeout is applied per request, proven with `pg_sleep(10)`

## Phase 4: Production Habits

### Story 13: Add middleware

**As an operator, I want every request logged with timing and a request ID.**

- **Concept:** higher-order functions, `http.Handler` wrapping, `log/slog`
- **Done when:**
  - Logging middleware emits structured logs (method, path, status, duration)
  - A request-ID middleware stores an ID in the context and returns it as a header
  - A panic-recovery middleware returns 500 instead of crashing

### Story 14: Test it properly

**As a developer, I want tests I trust so I can refactor fearlessly.**

- **Concept:** `testing`, table-driven tests, `httptest`, fakes via interfaces, subtests
- **Done when:**
  - Table-driven unit tests cover validation and `IsOverdue`
  - Handler tests use `httptest.NewRecorder` with `MemoryStore`
  - One integration test hits real Postgres (guard it with an env var or build tag)
  - `go test -cover ./...` reports above 70%

### Story 15: Remind me about overdue tasks

**As a user, I want to be notified when a task becomes overdue.**

- **Concept:** goroutines, channels, `time.Ticker`, `select`, `sync.WaitGroup`, worker pools
- **Done when:**
  - A scheduler goroutine ticks every 30 seconds, finds newly overdue tasks, and sends them on a channel
  - A pool of 3 workers receives them and "sends" a notification (log it first, then try a webhook call)
  - A task is never notified twice (track it with a `notified_at` column)
  - No goroutine leaks (verify by shutting down cleanly)

### Story 16: Protect the API

**As an owner, I want only authorized users to see and change tasks.**

- **Concept:** auth middleware, `context.WithValue`, password hashing (`bcrypt`), JWT
- **Done when:**
  - `POST /register` and `POST /login` exist, with the login returning a JWT
  - Tasks get a `user_id`, and every query is scoped to the logged-in user
  - Missing or invalid token → 401, another user's task → 404
  - Secrets come from config, never from source code

### Story 17: Ship it

**As an operator, I want to deploy a small, cleanly stopping container.**

- **Concept:** graceful shutdown (`signal.NotifyContext`, `server.Shutdown`), multi-stage Docker builds, cross-compilation
- **Done when:**
  - `SIGTERM` lets in-flight requests finish and the reminder workers drain
  - A multi-stage Dockerfile produces an image under \~30 MB
  - `docker compose up` brings up the API and Postgres together

## Bonus Stories

- **Tags and search:** many-to-many tags table, plus full-text search with Postgres `tsvector`.
- **Recurring tasks:** model "every Monday" rules and generate the next occurrence on completion.
